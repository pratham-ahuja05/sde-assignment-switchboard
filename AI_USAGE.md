# AI Usage Disclosure

## Tools used
- **Claude Code** (an AI coding agent) in VS Code. I used no other AI tools.

## What I used them for
- **Understanding the problem:** comparing assignments A and B, and reading the mock provider's
  source to learn exactly how it behaves: when a 504 means "placed" vs "not placed", when the
  tenant slot is freed, and how webhooks are retried.
- **Writing the code:** most of the first-draft code in `solution/switchboard/` and the tests in
  `solution/tests/` were generated by the AI from the design below, then run and corrected
  against the real mock.
- **Building the test tooling:** the chaos harness (`chaos.py`), the crash points (`crash.py`),
  the independent rule checker (`audit.py`) and the dashboard.
- **Debugging:** profiling why the first end-to-end run had window violations (see below).
- **Drafting docs:** the first drafts of `SUBMISSION.md` and this file, which I then edited.

## What I wrote or decided myself
- **Chose assignment B** over A. The failure-handling problem (crashes, 504s, lost webhooks)
  interested me more than report formatting.
- **Accepted or pushed for these design choices**, and can explain why each is safe:
  - SQLite as the single source of truth, instead of Temporal. One file, nothing to install, and
    `BEGIN IMMEDIATE` makes "check free slots + reserve one" a single atomic step.
  - **Deterministic request IDs** (`campaign + lead + attempt number`) instead of random ones, so
    a restarted process always regenerates the same ID for the same attempt.
  - **Save before you call:** the decision to dial is saved before the HTTP request is sent.
  - **Treat "unknown" as busy:** an unresolved call keeps holding its tenant slot and phone.
- **Scope:** kept to the core rules plus stretch goals I can explain (callback lateness,
  observability). I deliberately did not claim the "two dispatchers at once" stretch, because the
  in-flight protection is per process; this is written up as a known limit in `SUBMISSION.md`.
- **Repository:** made it public as the submission form asks, and removed the unused assignment A
  folder.
- **Verified the results myself** by running the tests and the chaos runs, and reading the
  scorecards (see below).

## What I can explain and defend
The parts I studied closely and expect to be asked about:

| Topic | Where | The idea in one line |
|---|---|---|
| At-most-once dialling | `engine.py` `request_id()`, `tick()` | Same attempt → same ID → the provider places at most one call for it |
| Write-ahead intent | `engine.py` `tick()` | Save the decision and reserve the slot *before* the network call; a crash leaves us over-reserved, never under |
| Ambiguous 504 | `engine.py` `place()`, `reconcile_intent()` | Don't guess: ask the provider `GET /v1/calls?request_id=`. Found = adopt, 404 = release and reuse the same ID |
| Lost webhooks | `engine.py` `watchdog()` | Poll calls that have been active too long |
| Duplicate webhooks | `engine.py` `handle_result()` | An attempt can move to `ended` only once; later copies are ignored |
| Webhook security | `app.py` `verify_signature()` | HMAC-SHA256 over the raw body, compared in constant time |
| Calling windows | `schedule.py` | `is_open` / `next_open`; campaign window ∩ 09:00–21:00; start inclusive, end exclusive |
| What happens after a call | `policy.py` `after_result()` | completed > exhausted > dnd_blocked; retry +60/+60/+15 min; callbacks at `callback_at` |
| Who to call next | `policy.py` `plan_dispatch()` | callbacks > retries > fresh; tenant limit shared across campaigns; one call per phone |
| Lead lifecycle | `SUBMISSION.md` state diagram | ready → dialing → active → (ready again \| completed \| exhausted \| dnd_blocked) |

## Where the AI was wrong or unhelpful
1. **It assumed the provider would answer fast.** The first full run had **10
   `outside_calling_window` violations**. In the database, some calls "lasted" 50 simulated
   minutes, but the mock caps calls at 6.5 minutes, so the provider itself was freezing. The cause:
   on my Windows laptop, creating an `httpx.AsyncClient` takes ~450 ms (it loads a certificate
   bundle), and the mock creates one for every webhook. At 600× speed that is ~4.5 simulated
   minutes per webhook, so calls decided at 18:59 arrived at 19:04. Fixes:
   - The dispatcher now measures request latency and stops starting calls that much earlier
     before the window closes (`Engine.end_guard_s`).
   - On Windows, the chaos harness gives the mock a one-certificate `SSL_CERT_FILE`, without
     changing the mock's code.
2. **A crashed lead lost its place in the queue.** When a call was confirmed "never placed",
   the first version reset the lead's `eligible_at` to "now", so fresh leads overtook it. A unit
   test (`test_crash_between_intent_and_post_never_double_dials`) failed and caught it. Now only a
   real backoff (after a 503) moves a lead back.
3. **Smaller fixes:** the tests first failed to import (relative imports without a package
   `__init__.py`), and one exhaustion test was so tangled I couldn't trust it, so it was
   rewritten on a single-lead setup.

## How I verified AI-generated code
- **Unit tests:** `pytest` runs 58 tests in about 1 s with a fake clock and a scriptable fake
  provider (503, 504 placed/unplaced, connection refused, duplicate and lost webhooks, and crashes
  simulated by restarting the engine on the same database).
- **Real end-to-end runs against the mock** with full failure injection, checked three ways:
  the provider's `/admin/report`, `final_state.csv` diffed against `/admin/leads`, and our own
  independent R1–R9 audit.

  | Run | Process deaths | Violations | Matches provider |
  |---|---|---|---|
  | seed 7, no failures | 0 | 0 | 200/200 |
  | seed 7, 6 hard kills + 14 injected crashes | 20 | 0 | 200/200 |
  | seed 2026 (unseen), 4 hard kills | 4 | 0 | 200/200 |
- **Reading the code:** I went through the core files (`policy.py`, `schedule.py`, `engine.py`)
  to make sure I can explain each decision and change it live.
